## Things that did not work as the documents say, or that look odd

- The SVG of a block (`image: true`) cannot be seen by the model; the client turns it into a saved file and text. The tool description's warning is right in the sense of "not seen", but there was no failure.
- `Card w=300` in the picture: the card is drawn 768 pixels wide (x=16, width=768) in an 800x600 SVG, so `w=300` seems not to be applied to the Card. The SVG also has `filter="url(#shadow)"` but no `<defs>` with a `shadow` filter. (Seen in the SVG text; not checked against the renderer.)
- The password placeholder is drawn as `••••`, not as "Enter password". (Seen in the SVG; may be intended.)
- Each tool accepts paths only relative to the session folder (repo root); a path relative to the file's folder fails with "no file by that name under E:\repos\HtmlConstruction".
- The after-write hook writes the SVG silently on success, so a model sees no sign that the picture was written; only `wireframe_check`/Glob shows it. The error message of the hook is shown as "blocking error" though the Edit itself succeeded.
- The skill text is written for the shell (`wire ...`); with the MCP server it says to use the MCP tools, but the "copy the old picture aside" step has no MCP route.

## Follow-up: what was done about the findings

- Card `w=300` and the undefined `shadow` filter: the current source already draws both right (built and rendered the same `spec.md`: card `width="300"`, `<defs><filter id="shadow">` present). The installed `wire` is v0.0.9 and older than the source; the two oddities came from that build. Fix: reinstall the global tool from the source (not done here; it changes the user's tool install).
- Password placeholder drawn as `••••`: the renderer does this on purpose (the type indicator replaces the placeholder). Not changed.
- Path rules: already stated in the MCP server's instructions and tool descriptions ("relative to the folder the server was started in"). Not changed.
- Skill copy-aside step with no shell: `plugin/skills/wireframe-update/SKILL.md` now says what to do without a shell. Changed.
- Hook text "blocking error" on a good Edit: comes from the host's wording of a hook that exits non-zero; not changed.
- Reinstalling the global tool was tried three times (also after a reboot) and refused each time: `Access to the path '...\.store\wireframe.cli\0.0.9' is denied`. Every open session runs `wire mcp` from those files. Answer, after Bruinet's `mcp-host`: `wire mcp-host` ([300-McpServer.md](300-McpServer.md)), the plugin's `.mcp.json` now starts it, and `dotnet/update-mcp.ps1` puts a new build where it runs from. Tested in `McpHostTests`. The global tool was then updated to 0.1.0 (the running `wire.exe` processes ended first); the trial's picture rendered again with it has the 300-pixel card and the `shadow` filter, and `wire mcp-host` from the installed tool answered `initialize` and `tools/list` and filled `%LOCALAPPDATA%\wire\mcp`. The installed plugin was then updated from 0.0.9 to 0.1.0 (`claude plugin marketplace update wireframes`, `claude plugin update wireframe@wireframes`, with the desktop app's own `claude.exe`; the `claude` on the path, an old npm install, crashes). `claude mcp list` in the repository: `plugin:wireframe:wireframe: wire mcp-host - ✔ Connected`. Not yet seen: a model session using the tools through the host, and a restart of the server under a live session after `update-mcp.ps1` (only `McpHostTests` shows that).
