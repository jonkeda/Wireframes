# 2. The command-line tool

Part of [the plan](000-Readme.md). `wire`, in .NET: a wireframe in, an SVG out. It is what the skills and the hooks
call, so it must start fast, say plainly what is wrong, and never surprise a script.

## The same tool as today's, and three things more

The TypeScript `wire` (`packages/cli`) stays as it is. The .NET tool takes the same arguments and gives the same
exit codes, so a script works with either.

| Call | Does | In the TypeScript tool |
| --- | --- | --- |
| `wire <file.wire>… [-o <path>]` | Renders each file to an SVG beside it, or to the output path; `-o -` writes to standard output | Yes |
| `-t, --theme <name>` | `clean`, `sketch`, `blueprint`, `realistic` | Yes |
| `-w, --width <n>`, `-h, --height <n>` | The SVG's width; its minimum height | Yes |
| `-v, --validate` | Checks only; writes nothing | Yes |
| `-f, --force` | Writes the SVG also when the source has errors the parser recovered from | Yes |
| `--watch` | Renders again when a file changes | Yes |
| `-c, --config <file>`, `-q, --quiet`, `--help`, `--version` | | Yes |
| `wire <file.md>…` | **New.** Renders every `wireframe` block of a Markdown file | No |
| `--json` | **New.** Diagnostics and results as JSON on standard output | No |
| `--check` | **New.** Writes nothing; exit 1 when an SVG is missing or is not what its source renders to now | No |
| `--stdin` | **New.** Reads one wireframe from standard input | No |
| `wire components [<name>] [--json]` | **New.** The language's controls and components with their attributes and modifiers, from the parser's own tables | No |

The first three new ones are what an agent needs: Markdown is where the wireframes are, JSON is what a tool reads,
and `--check` is what a build and a hook ask.

## Wireframes in Markdown

A specification holds its screens as fenced blocks:

````markdown
```wireframe
wireframe clean
    Card w=300
        Label "**Login**"
/wireframe
```
````

`wire spec.md` renders each block to a file beside the document, and changes nothing in the document.

A block's id is new with this plan: a word after the fence's language (`` ```wireframe id=login ``). The language
itself is not changed by it; whether the Markdown preview of the VS Code extension accepts the extra word is to
be checked.

| Question | Rule |
| --- | --- |
| The file's name | `<document>.<id>.svg` when the block has an id, else `<document>.<n>.svg` with the block's number in the document |
| Where | Beside the document; `--out-dir <folder>` puts them elsewhere, in the same folder layout |
| A block that moved | An id keeps its file. A number does not: a block inserted above renames the ones below. The tool says so once and suggests ids |
| A block that went | Its SVG is deleted, when the tool wrote it (it knows by the first line it writes into each SVG) |
| The picture in the document | Not the tool's business by default. `--link` writes or updates an image line under each block (`![login](spec.login.svg)`), between two marker comments, and touches nothing else |

Every SVG the tool writes starts with one comment: the tool's version, the source's hash and the options. `--check`
reads that line, so it never renders to compare, and a file a person drew by hand is never deleted.

## What it says

To a person, on standard error, one line per problem, in the form editors and build logs understand:

```text
spec.md(41,9): error WF012: 'TextImput' is not a control. Did you mean 'TextInput'?
```

The line and column are the document's, not the block's.

With `--json`, on standard output:

```json
{ "files": [ { "source": "spec.md", "block": "login", "svg": "spec.login.svg", "written": true,
               "diagnostics": [ { "severity": "error", "code": "WF012", "line": 41, "column": 9, "message": "…" } ] } ] }
```

| Exit code | Means |
| --- | --- |
| 0 | Done; with `--validate` or `--check`: nothing wrong |
| 1 | A source has errors, or with `--check` an SVG is stale or missing |
| 2 | The call itself is wrong: an unknown option. (A file that is not there is exit 1, as in the TypeScript tool: corrected 2026-11-19 after step 4) |

## Without Node

Decided by the owner (2026-11-19): the tool ships without Node. Nothing in it starts Node, and neither its build
nor its tests need it: the conformance set it is tested against is checked in as files.

## Packaging

| As | For |
| --- | --- |
| A .NET tool (`dotnet tool install wireframe.cli`), run as `wire` | A developer's machine and a build agent that have .NET |
| A single file per platform, compiled ahead of time | The hooks: it starts in some tens of milliseconds, where a .NET tool takes a few hundred |

The second matters. A hook that runs after every edit of a Markdown file must not be felt.

## Tests

- The TypeScript tool's own tests for its arguments, run against the .NET tool: same arguments, same exit code,
  same output file.
- Markdown: a document with three blocks, with and without ids; a block added above; a block removed; `--link`
  run twice gives the same document.
- `--check` after a render says nothing; after an edit of a block it names that block and no other.
- A file held by another program: tried again for a second, then reported, never half-written. An SVG is written
  to a temporary file and moved.

## Not in the first version

- PNG. Decided by the owner: SVG now, PNG from SVG later. The option's place is kept: `--format svg` is the
  default and the only value, so `--format png` can come without changing a call.
- A formatter for the wireframe text.
- Rendering a block from a file of another kind than Markdown.
